## 4. Аудит рекомендаций

### 4.1. Как устроен путь «анкета → карточка»

- **LLM для объяснений и первых фраз в проекте нет.** Оба текста собираются по шаблонам из `templatesByLocale` (`server/src/matching/recommend.ts:25-104`). `AGENTS.md:17`: «команда использует локальный подбор».
- **Демо-режим** (`src/App.tsx:262`): `startRecommendationSession(profile, candidates)` → `recommend()` в браузере по 150 профилям из `profiles.json`. Сервер не участвует.
- **Серверный режим:** `PUT /events/{id}/profile` сохраняет name, role, skills, experienceYears, interests, about, goal, lookingFor, visible и consentVersion (`server/src/profiles.ts`). `GET /events/{id}/recommendations` выбирает видимых участников события без блоков, ограничений и прошлых отметок (`server/src/recommendations.ts`), затем вызывает тот же `recommend()`.
- **Алгоритм** (`recommend.ts`, `recommend` и `scoreCandidate`):
  1. Жёсткий фильтр по взаимной цели.
  2. Для `hire` и `find_job` обязательно совпадение навыков. Если у нанимающего заполнен `lookingFor`, используется пересечение его `lookingFor` с навыками соискателя. Иначе используются общие навыки (PR #132, `:170-177`).
  3. Скор = 8 × (искомые навыки в обе стороны) + 4 × общие навыки + 2 × общие интересы + 1 за направление опыта в менторстве.
  4. Сортировка по скору, при равенстве по `id`. Берутся первые пять.
  5. Объяснение = фраза о цели + до двух причин. Первая фраза строится от первого совпадения, а при его отсутствии от первого навыка кандидата (`makeIcebreaker`, `:149-153`).
- **Нормализация:** регистр, пробелы, NFKC, 9 алиасов навыков (js, ts, postgres, node.js, react.js, vue.js…), группы ролей backend/frontend/fullstack/ios/android и, с PR #135, одна опечатка в известной роли (≥6 букв).
- **Ollama (PR #135, опционально):** только в серверном режиме, только для `hire`/`find_job` и только для «ролевых» фраз вида «… developer/engineer/разработчик». Модель сопоставляет такие фразы одной из пяти ролей. По умолчанию выключено (`TANYS_OLLAMA_URL` пуст). На объяснения не влияет.

### 4.2. Кейс Backend ↔ iOS/Swift

**Условия.** Одно событие. Участник A выбирает `hire`: роль «Тимлид бэкенда», навыки Go, PostgreSQL, Docker, «Какие навыки ищете» — «Backend Developer, Go, PostgreSQL». Swift ни в одном поле нет. Участник B выбирает `find_job`: роль «iOS Developer», навыки Swift, SwiftUI. Навыки A и B не пересекаются. Контрольный участник C выбирает `find_job`: «Backend Developer», Go, PostgreSQL.

**Вывод.** На `main` ошибка исправлена. **Подтверждённая причина в старой версии:** этап ранжирования `scoreCandidate` в `server/src/matching/recommend.ts` не требовал совпадения навыков для найма. Кандидат с `score = 2` (только общий интерес) или `score = 0` попадал в топ. `makeIcebreaker` при пустом `topic` брал `candidate.skills[0]`, то есть незапрошенный Swift. Исправлено в `31e08e4` (`hiringMatch`, строки 170-177). **На публичном демо ошибка воспроизводится,** потому что оно собрано до исправления (D01).

**Связанные дефекты, найденные на `main`:**
- **Ложноотрицательный результат по роли (D04).** Если A пишет в «Какие навыки ищете» только «Backend Developer», C («Backend Developer», Go, PostgreSQL) **не находится: 0 карточек**. Причина: `candidate.role` нигде не сравнивается, а «backend» ищется только среди навыков кандидата.
- **Нанимающий без `lookingFor` с нетехническими навыками** (HR, навыки «Подбор») получает 0 карточек. Поле «Какие навыки ищете» помечено как необязательное (API-тест, пользователь `d`).
- **Алиасы.** Совпадают: PYTHON/python, JS, TS, Postgres, NodeJS, React.js, Backend Developer ↔ Backend, Frontend ↔ Front-end. **Не совпадают:** Go ↔ Golang, Kubernetes ↔ k8s, Node.js ↔ Node, Python ↔ Питон, FastAPI ↔ Fast API, Next.js ↔ NextJS, Machine Learning ↔ ML, UX-исследования ↔ UX research, Computer Vision ↔ Компьютерное зрение.

### 4.5. Качество объяснений и первых фраз

- **Плюсы.** Тексты строятся только из реальных полей пары. Выдуманных навыков, опыта и намерений не обнаружено. Язык шаблона соответствует выбранному языку интерфейса (kk/ru/en). Это проверено в демо и через API с `?locale=`.
- **Минусы:**
  - Повтор одних и тех же навыков: «у участника есть нужные вам навыки: Go, PostgreSQL, **общие навыки: Go, PostgreSQL**» (D14).
  - Без совпадений объяснение вырождается в одну фразу о цели («Вы оба хотите обменяться опытом.»). Первая фраза тогда ссылается на первый навык кандидата, который не связан с запросом. Именно этот путь в старой версии давал «Swift».
  - Вопросы первой фразы фиксированы по цели. В пределах одной цели все 5 фраз отличаются только именем и одним навыком.
  - Значения из датасета не переводятся: «Hi Қанат А.! I saw "React"…». Если имя оканчивается точкой, получается двойная пунктуация «А.!».
- **Резервный режим без LLM.** LLM в тексты не встроена, поэтому отдельного резервного режима нет. Объяснения всегда детерминированы. Для Ollama-сопоставления ролей ошибка модели не создаёт совпадений («если модель недоступна или не уверена, новый вариант не засчитывается», `skill-ai.ts`, catch-блок). Правила совместимости при этом сохраняются: проверено с недоступным адресом Ollama, выдача не изменилась.

### P1

**D03 · Нет порога релевантности для ментора, кофаундера и обмена опытом**
- **Где:** `server/src/matching/recommend.ts`, `recommend()` и `scoreCandidate()`. В топ попадает любой кандидат со взаимной целью, даже при `score = 0`.
- **Шаги:** демо, цель «Найти ментора», роль iOS Developer, навыки Swift, ищу SwiftUI, Combine.
- **Ожидается:** 0–N релевантных и честное «найдено N из 5».
- **Фактически:** 5 Go- и UX-менторов, причина «у ментора больше лет опыта», первая фраза про Go. Аналогично с «Обменяться опытом» и «Найти кофаундера» (4.3).
- **Влияние:** прямое снижение оценки «качество рекомендаций» на анкетах жюри.
- **Исправление:** требовать хотя бы одно пересечение навыков, искомых навыков или интересов. Для ментора учитывать опыт только вместе с пересечением. Тест: iOS-менти → 0 карточек и сообщение «2 из 5».

**D04 · Роль не участвует в подборе, ложноотрицательные результаты при найме**
- **Где:** `scoreCandidate()`. `candidate.role` и `input.role` не сравниваются.
- **Шаги:** нанимающий пишет в «Какие навыки ищете» только «Backend Developer». Кандидат: роль Backend Developer, навыки Go, PostgreSQL.
- **Ожидается:** кандидат найден.
- **Фактически:** 0 карточек. HR без `lookingFor` с навыком «Подбор» тоже получает 0.
- **Исправление:** сравнивать нормализованную роль кандидата с `lookingFor` (группы ролей уже есть в `roleAliases`). Если у нанимающего `lookingFor` пуст, подсказывать его заполнить.

**D05 · Кофаундер: похожие ранжируются выше дополняющих; англоязычный ввод не совпадает**
- **Шаги:** анкета J3 (4.4).
- **Фактически:** 2/5. Причины подтверждены (4.4).
- **Исправление:** для `find_cofounder` дать вес 8 только встречному `lookingFor` и снизить вес общих навыков. Добавить двуязычные алиасы: sales ↔ продажи, product ↔ продукт, computer vision ↔ компьютерное зрение, golang ↔ go, k8s ↔ kubernetes, node ↔ node.js и др.

**D06 · Пробелы датасета: нет iOS, Swift и мобильных профилей, всё на русском, мало нанимающих по ряду стеков**
- **Доказательство:** 0 Swift и iOS из 150. Соискатель-фронтендер может получить максимум 5 нанимающих. 4 из 25 нанимающих профилей получают 0 карточек.
- **Влияние:** на анкете жюри «мобильный разработчик» выдача пустая.
- **Исправление:** добавить 20–30 синтетических профилей (iOS, Android, QA, GameDev, 1С, DevRel, продажи), часть с английскими значениями. Повторить покрытие скриптом из раздела 4.3.

**D07 · Позиция экрана после отправки: заголовок результатов не виден** (U1 и U2)
- **Шаги:** заполнить анкету → «Найти участников» на 390 и 1440.
- **Фактически:** на телефоне видны середина и низ списка, на ноутбуке заголовок закрыт шапкой (`assets/d-390-…`, `assets/d-1440-…`).
- **Исправление:** `scroll-margin-top` и прокрутка к началу результатов.

**D08 · Серверный режим не готов к живому демо «с нуля»**
- (а) Датасет не импортируется: БД пуста, сид-скрипта нет.
- (б) Видимость анкеты выключена по умолчанию (U13).
- (в) Выдача не обновляется при входе новых участников (U14).
- (г) Лимит **12 регистраций на один IP за 15 минут** (`server/src/auth.ts`, `consumePasswordAttempt(... registration ? 12 : 80)`). Подтверждено: 13-я регистрация вернула 429 «Слишком много запросов». На площадке с общим Wi-Fi (NAT) больше 12 человек за 15 минут не зарегистрируются.
- **Влияние:** если демо пойдёт в серверном режиме, топ будет почти пустым, а регистрация жюри может упереться в лимит. Демо-режим не затронут.
- **Исправление:** для питча использовать демо-режим или заранее заполнить событие. Поднять лимит регистраций или считать его по устройству. Добавить кнопку «Обновить».

**D09 · Необязательный Ollama: недоступный адрес добавляет ≈2,2 с к каждому запросу**
- **Где:** `server/src/matching/skill-ai.ts`. В `catch` нет `remember()`, поэтому неудачный запрос повторяется при каждом обращении.
- **Шаги:** `TANYS_OLLAMA_URL=http://10.255.255.1:11434`, нанимающий с «Server-side developer» в `lookingFor` → `GET /recommendations` 6 раз.
- **Фактически:** 2207–2217 мс на каждый запрос.
- **Исправление:** кэшировать ошибку с TTL (circuit breaker), уменьшить таймаут до ≈800 мс. Реальную модель на целевом железе не проверяли.
