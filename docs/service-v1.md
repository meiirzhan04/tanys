# Tanys 1.0 — контракт публичного сервиса

Этот контракт задаёт интерфейс для реализации задач #45–#62. Демо на Vercel продолжает использовать вымышленные анкеты. Реальные участники появляются в продукте через регистрацию и приглашение организатора.

## Размещение и запуск

React обращается к относительному адресу `/api/v1`. Для пилота один сервер в согласованном регионе обслуживает статическую сборку и API под общим HTTPS-доменом. Контейнер API работает на Node.js 22 и TypeScript, PostgreSQL доступен ему по внутренней сети. Один экземпляр приложения и БД ограничивают начальные затраты. При выборе площадки в #48 и #58 капитан утверждает регион размещения основных данных, копий и почтового сервиса, месячную смету и ответственного. До этого — только синтетические данные локально и на staging.

Локальная схема для #45: Compose запускает БД с именованным томом, одноразовый процесс миграции и API. Readiness проходит после подключения к БД и применения миграций. Для разработки React проксирует `/api` к локальному серверу. Продакшен получает конфигурацию подключения и почты из секретов окружения. Сиды демо запускаются отдельно только для разработки.

## Идентификация и границы данных

Вход по одноразовому коду из письма через SMTP. Тот же путь восстанавливает доступ владельцу почты. Сервер хранит хеш проверочного секрета, срок, счётчик попыток и одноразовое состояние. Нормализованный адрес уникален. Отправка и проверка ограничены по адресу и источнику запроса. Обмен успешного кода на сессию атомарен. Сессия — случайный токен в HttpOnly cookie с Secure на HTTPS и SameSite=Lax. Изменяющие запросы браузера проверяют Origin. Выход и удаление аккаунта отзывают сессию. После восстановления доступа отзываются предыдущие сессии.

| Данные | Владелец и граница |
| --- | --- |
| Пользователь, адрес, контакты, согласия | Владелец аккаунта. Публичные ответы подбора содержат только разрешённые поля анкеты |
| Мероприятие, стенды, приглашения | Организатор своего события. Первого организатора назначает оператор; последующие роли выдаются явно |
| Участие и анкета | Уникальная пара событие + пользователь. Участник редактирует свою анкету и явно включает видимость |
| Оценка рекомендации, блокировка | Направленная пара участников одного события. Блок в любом направлении исключает пару |
| Запрос знакомства | Одна пара на событие. Отправитель отзывает, получатель принимает или отклоняет; контакт открывается обеим сторонам при принятии |
| Встреча | Участники принятого знакомства. Предложение времени в пределах события; подтверждает получатель, отменяет любая сторона |
| Жалоба и действия модератора | Автор видит подтверждение отправки. Организатор видит очередь своего события. Модераторские операции записываются с исполнителем и временем |

## HTTP API

Пути в таблице относительно `/api/v1`. `E`, `U`, `I`, `M`, `S` — идентификаторы из ответов. Сервер извлекает действующего пользователя из сессии. Все списки участников ограничены событием и правами; для растущих списков используются `limit` и непрозрачный `cursor`, ответ содержит `items` и `nextCursor`. Короткие примеры показывают существенные поля.

| Действие | Метод и путь | Пример тела → результат |
| --- | --- | --- |
| Получить код входа или восстановления | POST /auth/challenges | `{"email":"user@example.org","purpose":"login"}` → 202 `{"challengeId":"C"}`. Для восстановления purpose=recover. Одинаковый ответ для новых и существующих адресов |
| Войти или восстановить доступ | POST /auth/sessions | `{"challengeId":"C","code":"123456"}` → 200 `{"id":"U"}` и cookie |
| Текущий пользователь / выйти / удалить аккаунт | GET /me · DELETE /auth/session · DELETE /me | GET → `{"id":"U"}`; выход → 204. Удаление с недавним подтверждением доступа → 204 и очистка по #57 |
| Создать / изменить / завершить событие | POST /events · PATCH /events/E | `{"name":"IT Meetup","timeZone":"Asia/Almaty","startsAt":"2027-02-01T05:00:00Z","endsAt":"2027-02-01T12:00:00Z"}` → 201 `{"id":"E","status":"active"}`. PATCH `{"status":"closed"}` → обновлённое событие |
| Мои события / открыть событие | GET /events · GET /events/E | → `{"items":[{"id":"E","role":"organizer"}],"nextCursor":null}` / `{"id":"E","status":"active"}` |
| Пригласить / отозвать ссылку | POST /events/E/invites · DELETE /events/E/invites/I | `{"expiresAt":"2027-02-01T12:00:00Z"}` → 201 `{"id":"I","token":"…"}`; отзыв → 204 |
| Вступить / выйти | PUT /events/E/members/me · DELETE /events/E/members/me | `{"token":"…"}` → `{"role":"participant"}`; выход → 204 |
| Сохранить / прочитать анкету | PUT /events/E/profile · GET /events/E/profile | `{"name":"Алия","role":"Backend","skills":["Go"],"experienceYears":2,"interests":["API"],"about":"Ищу команду","goal":"find_job","visible":true,"consentVersion":"v1"}` → собственная анкета |
| Изменить контакт для обмена | PUT /me/contact | `{"value":"participant@example.org"}` → 204 |
| Получить рекомендации / оценить | GET /events/E/recommendations?locale=ru · PUT /events/E/feedback/U | → `{"items":[{"candidate":{"id":"U","name":"Алия"},"explanation":"…","icebreaker":"…"}]}`; `{"response":"met"}` или `{"response":"not_a_fit"}` → 204, заново загрузить подбор |
| Запросить знакомство / ответить / увидеть контакт | POST /events/E/introductions · PATCH /events/E/introductions/I · GET /events/E/introductions/I | `{"recipientId":"U"}` → `{"id":"I","status":"pending"}`; `{"status":"accepted"}` → новое состояние. GET принятой пары включает контакт при наличии разрешения |
| Входящие и исходящие | GET /events/E/introductions · GET /events/E/meetings | → `{"items":[{"id":"I","status":"pending","direction":"incoming"}],"nextCursor":null}`. Клиент обновляет списки при возврате во вкладку |
| Указать доступность / увидеть общие слоты | PUT /events/E/availability/me · GET /events/E/introductions/I/slots | `{"slots":[{"start":"2027-02-01T07:00:00Z","end":"2027-02-01T07:15:00Z"}]}` → 204; GET → `{"items":[{"id":"S","start":"…","end":"…"}]}` |
| Предложить / подтвердить / отменить встречу | POST /events/E/meetings · PATCH /events/E/meetings/M | `{"introductionId":"I","slotId":"S"}` → 201 `{"id":"M","status":"pending"}`; `{"status":"confirmed"}` → подтверждённое время |
| Состав, карта интересов, стенды | GET /events/E/members · GET /events/E/interests · GET /events/E/booths | Организатор видит участников; карта возвращает `{"topics":[{"name":"API","count":8}]}`; участник получает опубликованные стенды своего события с причиной рекомендации |
| Изменить стенды | POST /events/E/booths · PATCH /events/E/booths/S | `{"name":"Сообщество Go","topics":["Go"],"published":true}` → 201 `{"id":"S"}`; PATCH `{"published":false}` снимает стенд с показа |
| Блок / жалоба / модерация | PUT /events/E/blocks/U · POST /events/E/reports · GET /events/E/reports · PATCH /events/E/reports/I | Блок → 204; `{"subjectId":"U","reason":"spam"}` → 201 `{"id":"I"}`; очередь и решение `{"status":"resolved","action":"restrict"}` доступны организатору |

Запрос знакомства переходит из pending в accepted, declined или withdrawn. Встреча переходит из pending в confirmed, declined или cancelled; confirmed допускает cancelled. Повтор того же действия идемпотентен. Встречный запрос читает существующую пару. Для подтверждения встречи БД атомарно исключает пересечения интервалов для обоих участников. Времена хранятся в UTC, отображение использует часовой пояс мероприятия.

Ошибки имеют вид `{"error":{"code":"slot_conflict","message":"Слот занят"}}`. 400 — неверные поля, 401 — истекла сессия, 403 — запрещённое действие, 404 — отсутствующий или скрытый ресурс, 409 — конфликт состояния, 429 — ограничение частоты. В 5xx возвращается идентификатор для обращения в поддержку. Коды стабильны для локализации клиента.

## Совместимость и выпуск

Каждая миграция имеет порядковый номер, выполняется транзакционно под общей блокировкой и регистрируется в БД. Сначала добавляются совместимые поля, затем обновляется приложение и переносятся данные. Удаление старого поля выполняется отдельным релизом после проверки потребителей. Откат приложения должен работать с расширенной схемой. Изменения, ломающие внешний контракт, переходят в следующую версию API. Проверки #60–#62 используют два события и отдельные учётные записи; пилот и работа с реальными данными проходят по согласованным условиям #48 в рамках #63.
