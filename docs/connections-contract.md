# Знакомства, поиск и встречи — API-контракт

Источник истины — сервер. Клиент не хранит контакты и статусы локально, а после каждого действия перечитывает данные.
Все пути ниже относятся к `/api/v1`. Нужна cookie-сессия; `user_id` всегда берётся из сессии, а не из запроса.

## Три разные сущности

| Сущность | Где хранится | Кто видит |
|---|---|---|
| Логин (`users.username`/email) | `users` | только владелец; не отдаётся другим |
| Публичный handle (`users.handle`, `@parasat`) | `users.handle` | участники того же мероприятия через поиск и карточки |
| Приватный контакт | `user_contacts.value` | владелец; второй человек — только при `accepted` |
| Анкета мероприятия | `event_profiles` | по правилам видимости этого мероприятия |

## Публичный handle

- `GET /me` → `{ id, username?, handle: string|null, canCreateEvents }`
- `PUT /me/handle` `{ handle }` → `200 { handle }`
  - нормализация: обрезка пробелов, ведущий `@` убирается, регистр приводится к нижнему;
  - формат `^[a-z0-9_-]{3,32}$`;
  - ошибки: `400 invalid_handle`, `400 handle_reserved` (admin, support, tanys, organizer, root, api, help, me, moderator, system, security, settings, null, undefined), `409 handle_unavailable`.
- Смена handle не меняет логин. Старый `@handle` просто перестаёт находиться; ссылки по `userId` продолжают работать.

## Приватный контакт

- `GET /me/contact` → `{ value: string|null }` — только владельцу, чтобы профиль показывал сохранённое значение после перезагрузки.
- `PUT /me/contact` `{ value }` → `204`. Пустая строка удаляет контакт.
- До 256 символов. Отклоняются управляющие символы, `<`, `>` и схемы `javascript:`, `data:`, `vbscript:`, `file:` (`400 invalid_contact`).
- Контакт не индексируется поиском и не попадает в выдачу поиска, рекомендаций или список участников.
- Ссылкой на клиенте можно делать только `https:`, `mailto:` и Telegram `@name` → `https://t.me/name`; остальное показывается текстом.

## Поиск участников

`GET /events/:eventId/participants?q=<строка>&limit=<1..20, по умолчанию 8>`

```json
{
  "items": [
    {
      "userId": "uuid",
      "handle": "parasat",
      "name": "Parasat Dauletbai",
      "role": "iOS-разработчик",
      "goal": "find_job",
      "introduction": { "id": "uuid", "status": "pending", "direction": "outgoing" }
    }
  ],
  "query": "parasat",
  "minLength": 2
}
```

- Ищет только среди участников этого мероприятия с **видимой** анкетой. Исключаются сам пользователь, заблокированные пары и участники с ограничением модерации.
- `q` нормализуется так же, как handle. Порядок: точный handle, затем совпадение по началу handle, затем вхождение в имя анкеты.
- Меньше `minLength` символов → `200` с пустым `items` (запрос в базу не делается).
- Без членства → `404 not_found`. Лимит: 120 запросов в минуту на аккаунт → `429 try_later` с `Retry-After`.
- `introduction` — состояние знакомства с этим человеком в этом мероприятии или `null`.
- Наличие в поиске **не означает** совместимость по подбору: метку «подходит» показывать нельзя.

## Знакомства

Статусы (`IntroductionStatus`): `pending` → `accepted` | `declined` (решает получатель) | `withdrawn` (отзывает отправитель).
`accepted` и `declined` финальны. Для одной пары в одном мероприятии всегда одна запись (уникальный индекс по паре).

| Действие | Запрос | Ответ |
|---|---|---|
| Отправить | `POST /events/:e/introductions` `{ recipientId, message? }` | `201` новое; `200` уже существует (та же запись) |
| Список | `GET /events/:e/introductions` | `{ items: IntroductionItem[], nextCursor: null }` |
| Один | `GET /events/:e/introductions/:id` | `IntroductionItem` |
| Принять/отклонить | `PATCH …/:id` `{ status: "accepted" \| "declined" }` (только получатель) | `IntroductionItem` |
| Отозвать | `PATCH …/:id` `{ status: "withdrawn" }` (только отправитель) | `IntroductionItem` |

`IntroductionItem`:

```json
{
  "id": "uuid", "status": "pending", "direction": "incoming",
  "participantId": "uuid", "participantName": "Алия", "participantRole": "Backend",
  "participantHandle": "aliya", "message": "Привет! Обсудим Go?",
  "contact": null, "createdAt": "…", "updatedAt": "…"
}
```

Правила:
- `message` — необязательно, до 280 символов, управляющие символы удаляются; выводить как текст.
- `contact` заполнен **только** при `accepted` и только у двух участников пары; удаление контакта сразу даёт `null`.
- Встречный запрос (B→A, когда A→B уже ждёт) возвращает существующую запись; для B она `incoming` — показывать «Принять».
- Повторная отправка после `withdrawn` возможна только исходным отправителем (запись снова `pending`). После `declined` повторная отправка возвращает ту же запись со статусом `declined`.
- Обе анкеты должны быть видимы, нельзя писать себе, вне своего мероприятия, при блокировке или ограничении → `400 invalid_recipient` / `404 not_found`.
- Неверный переход → `403 forbidden_transition`; изменение финального статуса → `409 introduction_final`; закрытое мероприятие → `409 event_closed`.
- Лимит отправки: 30 запросов за 10 минут на аккаунт → `429 try_later`.

## Встречи (существующий механизм)

- `GET /events/:e/introductions/:id/slots` → общие свободные 15-минутные слоты пары (только при `accepted`).
- `POST /events/:e/meetings` `{ introductionId, slotId }` — `slotId` это ISO-время начала слота. Не на шаге 15 минут → `400 invalid_time_step`; слот занят или недоступен → `409 slot_conflict`.
- `PATCH /events/:e/meetings/:id` `{ status: "confirmed" | "declined" }` (получатель) или `{ status: "cancelled" }` (любой); отмена освобождает слот.
- Звонков в Tanys нет: после встречи показывайте только контакт, если он открыт.

## Участники мероприятия (организатор)

`GET /events/:e/members?limit=<1..100>&cursor=<userId>&q=<имя или handle>&goal=<цель>&visibility=visible|hidden|incomplete`

```json
{ "items": [{ "userId": "uuid", "role": "participant", "name": "Алия", "handle": "aliya",
  "profileRole": "Backend", "goal": "hire", "visible": true }], "nextCursor": "uuid|null", "total": 351 }
```

- Только организатор этого мероприятия (`403 organizer_required`, чужое — `404`).
- У скрытой анкеты `visible: false`, а имя, роль и цель не раздаются (имя = handle); поиск и фильтр по цели скрытые поля не учитывают.
- `visible: null` — анкета не заполнена. Email, логин и контакты не отдаются.

## Когда перечитывать

- После любого действия со знакомством или встречей — перечитать список (ответ уже содержит актуальную запись).
- При открытии вкладок «Запросы»/«Встречи», при возврате на вкладку браузера и при смене мероприятия; ничего не переносить между `eventId`.
- Показывать «Запрос отправлен» только после ответа `200/201`; при сетевой ошибке — ошибка и «Повторить».

## Политика при выходе, скрытии, блокировке, удалении

- **Выход из мероприятия** удаляет членство, анкету и знакомства этого мероприятия (каскад). Другие мероприятия не затрагиваются.
- **Скрытая анкета**: человек не находится в поиске, ему нельзя отправить запрос, существующие знакомства не показываются второй стороне.
- **Блокировка или ограничение модератором**: пара исчезает из поиска, списков и встреч; запросы запрещены.
- **Удаление аккаунта**: удаляются контакт, знакомства, встречи и анкеты; аккаунт организатора удалить нельзя (`409 organizer_owns_events`).

## Миграция `014_connections.sql`

- `users.handle` (уникальный, формат выше) заполняется текущим `username`, если он есть; у аккаунтов только с email handle пустой, пока владелец его не задаст.
- `introductions.message` (nullable, до 280 символов) — старые записи остаются без сообщения.
- `request_buckets` — счётчики лимитов на аккаунт (не на IP, чтобы общий Wi-Fi площадки не блокировал всех).
- Существующие контакты (`user_contacts`) и знакомства не меняются.
